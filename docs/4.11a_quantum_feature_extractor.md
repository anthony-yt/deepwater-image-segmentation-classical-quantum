# Task 4.11(a) — Quantum feature extractor in preprocessing (Alexis)

Part of 4.11. The question is whether the quantum part of the project should live in
preprocessing (extracting features) or stay in classification (as it is now, a VQC that
decides pipe vs. background).

## Where we are
In v3 the quantum part is a classifier (the angle-encoding VQC): it takes the 8 classical
features chosen on validation and outputs a pipe/background logit directly. The circuit is the
decision, not an extractor.

Moving the quantum part to preprocessing means changing the circuit's role: it would produce a
feature vector, and a classical model (an SVM) would make the final decision over that vector.
The pattern is already prototyped on this branch: the 4_qck_sobel_comparison notebook is a
quanvolutional kernel (4 qubits over 2x2 windows) that builds an edge map. 4.11 asks whether that
same idea helps as a feature front-end for the patch classifier.

## What would go in
A patch (currently 16x16) cannot be loaded whole into a few qubits, so it has to be reduced.
Three options, depending on the encoding:
1. Sliding 2x2 window (quanvolutional, Henderson 2019, what the QCK does today): the 4 pixels of
   each 2x2 window of the patch, normalized to angles, slid with a stride.
2. Amplitude encoding of a downsample: the patch reduced to 8x8 = 64 values as an amplitude
   vector (exactly what patch_amplitudes already does in v1).
3. Angle encoding of a classical summary: a few statistics of the patch, one per qubit.
In all three the input is pixels or statistics of the already-filtered patch, with the same masks
and splits as the rest of the pipeline.

## What would come out
A fixed-length real vector, not a label, built from the expectation values measured at the end of
the circuit: ⟨Z_i⟩ per qubit (n components), optionally the ⟨Z_i Z_j⟩ correlators (two-body signal,
where the circuit might capture something a linear summary cannot). In the quanvolutional variant,
4 channels per position give a feature map that is then pooled per patch. This vector replaces, or
is concatenated with, the 8 hand-crafted features, and an SVM consumes it. The key control (for
5.16) is a classical baseline of the same dimension (PCA to the same number of components), so the
circuit does not get credit for what is really just dimensionality reduction.

## How many qubits
| Variant | Qubits | Where the number comes from |
|---|---:|---|
| Quanvolutional 2x2 filter (current QCK) | 4 | one qubit per pixel of the 2x2 window |
| 3x3 filter | 9 | one qubit per pixel |
| Amplitude encoding of 8x8 | 6 | ceil(log2(64)) = 6 |
| Angle encoding of k features | k (today 8) | one feature per qubit (re-uploading can lower it) |

Recommendation for the 5.16 prototype: start at 4 qubits (the 2x2 filter already validated on this
branch) and, for more capacity, 6 qubits via amplitude encoding of the 8x8 downsample. Beyond ~10
qubits the simulator cost on CPU is not justified (see Mariana's part: measurement cost and noise).

## What this settles and what it does not
In favor: it separates representation from decision, and lets us measure whether the quantum
representation beats PCA of the same dimension with a fixed SVM as the judge, reusing code already
on the branch. Against: every component of the vector needs repeated measurements (shots) per patch
and per position, a cost that grows with the number of qubits and correlators; and noise degrades
exactly the two-body correlators, which are the interesting part. That is what Mariana evaluates
(part b) before we agree on a recommendation (part c).

## Input for the joint recommendation (part c)
Alexis's proposal: "it depends". Moving the quantum part to extraction makes sense only if the
5.16 prototype shows that the quantum vector (4 or 8 qubits) beats PCA of the same dimension feeding
the same SVM, at a measurement cost Mariana considers acceptable. Otherwise the quantum part stays
in classification, as in v3.
